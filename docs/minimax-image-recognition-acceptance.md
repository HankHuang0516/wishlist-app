# MiniMax `understand_image` 圖片辨識驗收

## 現況與限制

上傳照片後，原流程只把圖片網址當文字傳給 EClaw；有效 JSON 並不代表模型看過圖片。測試帳號曾發生兩個確定的跨品類誤判：願望 805 的公仔照片被寫成 iMac，願望 806 的白糖粿招牌被寫成 Polaroid 相機。這兩張圖的網址可下載，故障點不在上傳或圖片公開權限。

本次改為：下載已核准網域的照片 → 正規化圖片位元組 → 呼叫 MiniMax Coding Plan VLM（`understand_image` 的底層端點）→ 解析可見證據 → 將證據交給 EClaw 估價 → 名稱衝突時拒絕寫入。無視覺服務金鑰、圖片不可讀、無足夠證據或模型回覆不一致時，願望保留原始名稱與照片，AI 狀態標記失敗。

這是提示詞校準與系統驗證，不是重新訓練 MiniMax 模型。任何模型都不能保證未知照片 100% 正確；能承諾的是「未通過證據閘門不自動改寫」以及對固定驗收集計算真實通過率。

## 部署前必要條件

- 將 MiniMax Coding Plan 對應區域的 `MINIMAX_API_KEY` 設為 Railway 私密環境變數，不存進程式庫或文件。
- `MINIMAX_API_HOST` 使用 `https://api.minimax.io`（Global）或 `https://api.minimaxi.com`（中國區），必須與金鑰區域相符。
- 確認 `RAILWAY_PUBLIC_DOMAIN` 包含正式圖片網址的主機。其他受信任圖片主機可由 `MINIMAX_VISION_IMAGE_HOSTS` 逐一設定；不可放任意通配網域。
- 在測試環境用真正 MiniMax 金鑰跑端到端測試，確認實際產生可見證據，而不只驗證 mock 回覆。
- 未完成以上項目之前，不發布此流程到正式環境；否則新照片會安全失敗，但不會自動辨識。

## 高規格驗收

1. 用戶照片、產品包裝、複數商品、招牌／食物、模糊與非商品圖片建立至少 50 張經人工標註的私有驗收集；不把用戶原圖提交到 Git。
2. 固定回歸案例 805、806 必須 2/2 不再跨品類誤判；若無法確認，應標記需人工確認，不得虛構商品。
3. 統計主體品類 Top-1、名稱可接受率、品牌／型號誤報率、價格區間覆蓋率、拒答率，依商品類別分層呈現。固定驗收集目標為跨品類誤覆寫 0；不將有限測試結果宣稱為全域 100% 準確率。
4. 驗證 API 超時、金鑰遺漏、非圖片回應、超過 8 MiB、未核准網域、EClaw 名稱衝突均不覆寫願望；原始圖片仍可顯示。
5. 驗證影像內容只傳至已設定的 MiniMax 端點，API 金鑰不出現在日誌、資料庫、對話或測試輸出。

本地自動測試：`cd server && npm test -- --runInBand && npm run build`。目前的自動化測試驗證的是資料流與拒絕錯誤結果，不代表已完成真實 MiniMax 辨識準確率驗收。
